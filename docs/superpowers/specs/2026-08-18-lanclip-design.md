# lanclip — общий буфер обмена Mac ↔ Windows-ПК по локальной сети

Дата: 2026-08-18

## Задача

Перенос содержимого буфера обмена между Mac (`192.168.1.102`, macOS) и Windows-ПК
(`pc`, `192.168.1.184`) в локальной сети. Поддерживаемые типы: текст, растровая
картинка, файлы и папки. Вставка содержимого буфера соседней машины — по
глобальному хоткею **Ctrl+Shift+V** на обеих машинах.

## Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Модель обмена | pull по хоткею | Ничего не уходит в сеть, пока не нажат хоткей: нет утечки паролей из буфера, нет демонов-наблюдателей, нет конфликта «кто скопировал последним» |
| Транспорт | HTTP/JSON по LAN, общий токен | На Mac выключен sshd и нет `authorized_keys`; SSH-вариант требовал бы Remote Login + раздувал бинарные данные base64 |
| Агент на Mac | Swift-бинарь, LaunchAgent | `swiftc` в системе; полный доступ к `NSPasteboard` нужен всё равно для файлов и картинок, хоткей и сервер встраиваются в тот же процесс |
| Агент на Windows | C#-бинарь, компиляция `csc.exe` | PowerShell 7.6.5 на ПК не умеет `Get-Clipboard -Format Image/FileDropList`; C# даёт `RegisterHotKey` + `HttpListener` + полный `Clipboard` без установки SDK |
| Хоткей | Ctrl+Shift+V на обеих машинах | Единая мышечная память; на macOS не конфликтует с Cmd-пастом |

Отклонённые варианты: авто-push при копировании (утечка всего скопированного),
гибрид с историей буфера (лишний UI и код), SSH-транспорт, AutoHotkey +
PowerShell-сервер на Windows (два процесса и неполный доступ к буферу).

### Расхождения реализации с этой спекой (зафиксированы как принятые)

Эта спека — связывающая инстанция, поэтому расхождения помечаются явно, а не
остаются молчаливым дрейфом между документом и кодом. Ниже — весь текст

`"version":"<n>"` там, где встречался изначально; актуальные значения — здесь

| Место в спеке | Спека | Реализация | Почему |

## Архитектура

Полностью симметричные роли. На каждой машине один резидентный процесс, который
одновременно:

1. **сервер** — отдаёт содержимое *своего* буфера по HTTP;
2. **клиент** — по своему хоткею тянет буфер соседа, наполняет локальный буфер и
   синтезирует нажатие паста.

```
   Mac                                     Windows-ПК
┌────────────────────────┐             ┌────────────────────────┐
│ lanclipd (Swift)       │             │ lanclipd.exe (C#)      │
│  NWListener :8899      │◀───GET─────▶│  HttpListener :8899    │
│  NSPasteboard          │   /clip     │  Clipboard             │
│  RegisterEventHotKey   │   /clip/blob│  RegisterHotKey        │
│  CGEvent (Cmd+V)       │   /health   │  SendInput (Ctrl+V)    │
└────────────────────────┘             └────────────────────────┘
```

### Протокол

HTTP/1.1, порт `8899`, авторизация заголовком `X-Clip-Token` (общий секрет).
Запросы принимаются только с адресов приватных диапазонов; неверный или
отсутствующий токен → `401` без тела.

**`GET /health`** → `200 {"ok":true,"host":"<hostname>","version":"<n>"}`

**`GET /clip`** → манифест текущего буфера, одна из форм:

```json
{"kind":"empty","seq":41}
{"kind":"text","seq":42,"text":"…"}
{"kind":"image","seq":43,"blobs":[{"i":0,"rel":"clip.png","size":48213,"mime":"image/png"}]}
{"kind":"files","seq":44,
 "blobs":[{"i":0,"rel":"отчёт.pdf","size":91234},
          {"i":1,"rel":"img/a.png","size":5120}],
 "totalSize":96354}
```

`seq` — счётчик изменений буфера операционной системы:
`NSPasteboard.general.changeCount` на macOS, `GetClipboardSequenceNumber()` на
Windows. Клиент передаёт его обратно при загрузке блобов, и это единственный
механизм обнаружения того, что буфер уехал посреди передачи.

- Порядок определения типа: **файлы → картинка → текст**. Первое совпадение
  выигрывает.
- Папки обходятся рекурсивно; `rel` — относительный путь внутри партии,
  сохраняющий структуру (`img/a.png`). Для одиночных файлов `rel` — имя файла.
- `rel` всегда в UTF-8, всегда с прямыми слешами, нормализуется на приёме
  (никаких `..`, абсолютных путей и двоеточий Windows).
- Картинка всегда кодируется в PNG, независимо от исходного формата в буфере.
- Если `totalSize` превышает `maxBytes`, сервер всё равно отдаёт манифест —
  решение об отказе принимает клиент, чтобы показать внятное уведомление.

**`GET /clip/blob/{i}?seq={seq}`** → `200 application/octet-stream`, сырые байты,
стримом. Индекс `i` соответствует манифесту, `seq` — оттуда же. Если текущий
счётчик изменений буфера не равен переданному `seq`, сервер отдаёт `409` и клиент
прерывает партию, не трогая локальный буфер. Чтобы блобы не пересчитывались на
каждый запрос, сервер держит снимок последнего отданного манифеста вместе с его
`seq`: для текста — саму строку, для картинки — PNG-байты, для файлов — список
абсолютных путей.

**`POST /pull`** → агент выполняет цикл «резолв соседа → `/clip` → загрузка →
запись в локальный буфер» и отвечает результирующим манифестом. Пасты не
синтезирует. Это то же действие, что делает хоткей; отдельный эндпоинт нужен для
CLI и интеграционных тестов.

### Конфигурация

Один и тот же формат на обеих машинах: Mac `~/.config/lanclip/config.json`,
Windows `%USERPROFILE%\.config\lanclip\config.json`.

```json
{
  "port": 8899,
  "token": "<32 hex>",
  "peers": ["pc", "192.168.1.184"],
  "maxBytes": 536870912,
  "autoPaste": true
}
```

- `token` генерируется один раз и копируется на вторую машину.
- `peers` перебирается по порядку до первого ответившего `/health`; удачный адрес
  кешируется в памяти и переспрашивается при первой же ошибке. Это закрывает
  смену IP по DHCP: в конфиге ПК стоят `cab-wsm-0667615.local` (mDNS с ПК
  резолвится, проверено) и последний известный IP Mac.
- `maxBytes` — предел на суммарный размер партии, по умолчанию 512 МБ.
- `autoPaste: false` — только наполнить буфер, без синтеза нажатия.

### Стейджинг принятых файлов

Принятые файлы складываются в партию с временной меткой:

- Mac: `~/Library/Application Support/lanclip/incoming/<yyyymmdd-hhmmss>/`
- Windows: `%LOCALAPPDATA%\lanclip\incoming\<yyyymmdd-hhmmss>\`

В буфер кладутся локальные пути внутри партии, поэтому обычный Cmd+V / Ctrl+V в
Finder, Проводнике, мессенджере или почте вставляет настоящие файлы.

Уборка выполняется при каждом успешном pull: удаляются партии старше 7 дней и
всё, что выходит за 20 последних партий.

### Поток по Ctrl+Shift+V

1. Хоткей перехвачен агентом.
2. Резолв соседа (кеш, при ошибке — перебор `peers`).
3. `GET /clip`. `kind: "empty"` → уведомление «буфер соседа пуст», выход.
4. `totalSize > maxBytes` → уведомление с размером, выход.
5. Загрузка блобов: картинка — в память, файлы — стримом на диск в партию.
6. Запись в локальный буфер: текст — строкой; картинка — как картинка; файлы —
   списком путей (на macOS объявляются и `NSURL`-объекты, и легаси
   `NSFilenamesPboardType`, чтобы старые приложения тоже видели файлы).
7. Синтез нажатия паста, если `autoPaste`.

Успех тихий, кроме файлов — короткий тост «3 файла, 12 МБ». Любая ошибка —
уведомление (`osascript display notification` / tray balloon).

### Известные грабли, заложенные в дизайн

- **Зажатые модификаторы.** В момент синтеза Ctrl и Shift физически нажаты. Перед
  пастом обеим платформам нужно отправить key-up на Ctrl и Shift и синтезировать
  событие с чистыми флагами, иначе приложение получит Cmd+Ctrl+Shift+V и
  проигнорирует его.
- **Accessibility на macOS.** `RegisterEventHotKey` разрешений не требует, а синтез
  нажатия через `CGEvent` требует. Это разовая выдача в «Настройки →
  Конфиденциальность и безопасность → Универсальный доступ», привязанная к пути
  бинарника. Устанавливаем бинарь по стабильному пути и подписываем ad-hoc
  (`codesign -s -`), чтобы пересборка не сбрасывала разрешение.
- **Биндинг `HttpListener` на Windows.** Без прав администратора нельзя слушать
  `http://+:8899/`. Разовая настройка под админом: `netsh http add urlacl` для
  учётки `paulislava` и правило файрвола на порт 8899.
- **Сессия рабочего стола.** Доступ к буферу и хоткеям требует GUI-сессии: на Mac
  это LaunchAgent (не LaunchDaemon), на Windows — задача с триггером `-AtLogOn` и
  «запускать только при входе пользователя». Процессы, запущенные из SSH-сессии,
  на ПК умирают вместе с ней — автозапуск оформляется только через
  `Register-ScheduledTask`.

## Компоненты

Каждый компонент отвечает на «что делает, как используется, от чего зависит» и
тестируется отдельно.

| Компонент | Ответственность |
|---|---|
| `Config` | Чтение и валидация конфига, генерация токена при первом запуске |
| `PeerResolver` | Перебор `peers` по `/health`, кеш живого адреса, инвалидация при ошибке |
| `ClipboardReader` | Снимок локального буфера → манифест + доступ к байтам блобов |
| `ClipboardWriter` | Манифест + локальные пути → запись в локальный буфер |
| `HttpServer` | `/health`, `/clip`, `/clip/blob/{i}`, `/pull`, проверка токена и адреса |
| `PullClient` | Резолв, `/clip`, загрузка блобов, стейджинг, вызов `ClipboardWriter` |
| `Staging` | Создание партий, нормализация `rel`, уборка старых партий |
| `HotkeyBinder` | Регистрация Ctrl+Shift+V, вызов `PullClient`, синтез паста |
| `Notifier` | Уведомления об ошибках и тост про файлы |
| `Cli` | Подкоманды `serve`, `status`, `get`, `pull` |

Границы держатся так, что `PullClient` и `HttpServer` не знают про платформенный
буфер — они работают через интерфейсы `ClipboardReader` / `ClipboardWriter`. Это
позволяет тестировать протокол с подставным буфером.

## Тестирование

Подкоманды CLI делают всё, кроме самого хоткея, проверяемым без GUI. Интеграционные
сценарии гоняются с Mac, вторая сторона дёргается по SSH (`ssh paulislava@pc`).

Уровни:

1. **Юнит** — нормализация `rel` (обход `..`, двоеточия, кириллица), разбор
   конфига, проверка токена, отказ по `maxBytes`, парсер HTTP-запроса на Mac.
2. **Протокол с подставным буфером** — `ClipboardReader`/`Writer` подменяются
   фикстурами, поднимается реальный сервер на localhost, проверяются все `kind`,
   `401` на неверном токене, `409` на смене буфера между `/clip` и `/clip/blob`.
3. **Кросс-машинная интеграция** — `lanclip get` и `lanclip pull` между Mac и ПК
   в обе стороны.
4. **Ручная проверка хоткея** — по матрице ниже, на обеих машинах.

Матрица содержимого: текст ASCII, текст с кириллицей и emoji, многострочный
текст, скриншот, один файл, много файлов, папка с вложенностью, имена с
пробелами и кириллицей, пустой буфер, сосед выключен, неверный токен, партия
больше `maxBytes`.

## Вне объёма

Богатый текст (RTF/HTML) — переносится как plain text. История буфера и выбор из
нескольких элементов. Работа вне локальной сети. Синхронизация более двух машин.
Авто-push при копировании.
