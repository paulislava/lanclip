# lanclip — проект

Общий буфер обмена между Mac и Windows-ПК Павла по локальной сети: то, что
скопировано на одной машине, забирается на другой одним глобальным хоткеем
**Ctrl+Shift+V** (одно и то же сочетание на обеих платформах).

## Топология

| | Mac | ПК |
|---|---|---|
| IP в LAN | `192.168.1.102` | `192.168.1.184` |
| Имя в сети | mDNS `cab-wsm-0667615.local` | `DESKTOP-NGNE28E`, запись `pc` в `/etc/hosts` Mac |
| Учётка | (текущий пользователь Mac) | `paulislava` |
| Порт | **8901** | **8901** |

Порт **8901**, не 8899: 8899 занят на Mac посторонним процессом `server.py`,
не имеющим отношения к lanclip.

Оба агента используют один и тот же `config.port` и для собственного сервера,
и для обращения к порту соседа — см. ограничение №3 ниже.

## Протокол

HTTP/1.1, авторизация заголовком `X-Clip-Token`, общий 32-символьный
hex-токен в конфигах обеих машин. Полное описание запросов/ответов —
`proto/PROTOCOL.md`. Коротко: `GET /health`, `GET /clip` (манифест буфера),
`GET /clip/blob/{i}?seq={seq}` (байты одного блоба), `POST /pull` (агент сам
тянет буфер соседа и кладёт в свой).

## Где что лежит

**Mac:**
- бинарник — `~/.local/bin/lanclipd` (стабильный путь + подпись сертификатом
  разработчика с фиксированным идентификатором, НЕ ad-hoc —
  разрешение Accessibility привязано к обоим);
- конфиг — `~/.config/lanclip/config.json` (права `0600`);
- лог — `~/Library/Logs/lanclip.log`;
- LaunchAgent — `~/Library/LaunchAgents/space.paulislava.lanclip.plist`,
  label `space.paulislava.lanclip`, `RunAtLoad`+`KeepAlive`;
- стейджинг входящих файлов — `~/Library/Application Support/lanclip/incoming`.

**ПК:**
- бинарник — `%USERPROFILE%\.local\bin\lanclipd.exe`;
- конфиг — `%USERPROFILE%\.config\lanclip\config.json`;
- автозапуск — задача планировщика `lanclip` (триггер `-AtLogOn`,
  `-LogonType Interactive`, скрытая через `powershell.exe -WindowStyle Hidden`);
- стейджинг входящих файлов — `%LOCALAPPDATA%\lanclip\incoming`.

Исходники: `mac/Sources/...` (Swift Package, `LanClipCore` + исполняемый
`lanclipd`), `win/src/...` (C# 5 / .NET Framework 4.8, компилируется
`csc.exe` без Roslyn и без NuGet/SDK — см. `ai/ERRORS.md`).

## Сборка и установка

**Mac** (собирает и ставит в одном скрипте, идемпотентно):
```bash
./scripts/install-mac.sh
```
Подробности первого запуска и разрешений — `docs/mac-setup.md`.

**ПК** — код и установочный скрипт сначала доставляются с Mac по SSH/scp
(`scripts/sync-win.sh` собирает; `scripts/install-win.ps1` ставит службу).
Установка на ПК требует прав администратора (нужны `netsh http add urlacl` и
`New-NetFirewallRule`) и выполняется на самом ПК:
```powershell
# из PowerShell на ПК с правами администратора, после того как код доставлен
& C:\Users\PaulIsLava\lanclip\scripts\install-win.ps1
```

Оба скрипта идемпотентны: существующий `config.json` не перезаписывается —
токен внутри может быть уже согласован со второй машиной.

## Обмен токеном

Токен генерируется автоматически при первой установке
(`scripts/gen-token.sh` на Mac, эквивалентный код в `install-win.ps1` на
ПК — оба через `RandomNumberGenerator`/`/dev/urandom`, 16 байт → 32 hex-
символа). Чтобы машины узнавали друг друга, значение `token` в обоих
`config.json` должно совпадать буквально — вписывается вручную один раз
после установки. Заодно в `peers` каждой машины дописывается адрес другой
(``["pc", "192.168.1.184"]`` на Mac, ``["cab-wsm-0667615.local",
"192.168.1.102"]`` на ПК — так они прописаны сейчас, задача 26).
`PeerResolver` перебирает `peers` по порядку и кеширует первый живой адрес,
поэтому по два варианта в списке безопасны: если один не резолвится или не
отвечает, резолвер просто пробует следующий.

## Логи и диагностика

```bash
tail -n 50 ~/Library/Logs/lanclip.log                 # Mac, лог агента
launchctl print gui/$(id -u)/space.paulislava.lanclip  # Mac, состояние LaunchAgent
~/.local/bin/lanclipd status                           # Mac, порт/буфер/сосед
```
```powershell
Get-ScheduledTask lanclip                              # ПК, состояние задачи
Get-Process lanclipd                                   # ПК, жив ли процесс
```

Кросс-машинная проверка целиком — `scripts/smoke.sh` (см. README.md и
раздел «Известные ограничения» ниже про прокси).

## Известные ограничения

Полный список — `ai/FEATURES.md` и `README.md` (раздел «Известные
ограничения»); из архитектурно значимого:

1. Диагностика с Mac (`curl` и т.п.) уходит через корпоративный прокси и
   получает `503` от него — не от соседа. Нужен `--noproxy '*'`. Сами агенты
   не через прокси не ходят.
2. SSH-сессия на ПК живёт в `SessionId=0` с изолированным пустым буфером;
   агент и рабочий стол — в `SessionId=1`. Буфер ПК по SSH не увидеть.
3. `config.port` — один порт на обе роли (свой сервер и адрес соседа). Смена
   порта на одной машине без второй молча рвёт связь.
4. Симлинки на каталоги внутри скопированной папки молча пропускаются при
   обходе — манифест окажется неполным без предупреждения.
5. Автоподъём задачи планировщика после падения процесса (`RestartCount`/
   `RestartInterval`) не подтверждён экспериментом. Автозапуск при входе в
   систему — подтверждён.
6. Триггер `-AtLogOn` не проверен настоящим циклом выхода/входа в систему —
   только структурно.
7. Число попыток `pull` нигде не видно пользователю: при `changedMidTransfer`
   делается один автоповтор, и «с первой попытки» неотличимо от «со второй».
8. Причина гонки `409 changedMidTransfer` на Windows (~20% в одном сценарии)
   не установлена — повтор её гасит, но не объясняет.
9. Легаси `NSFilenamesPboardType` на Mac нельзя проверить удалением строки —
   macOS синтезирует этот тип сама.
10. Лимит длины пути — 150 байт UTF-8 на компонент, 400 байт UTF-8 на весь
    путь. Длинные неанглийские имена файлов отвергаются там, где английские
    прошли бы.

Разрешения **Accessibility** и **Local Network** на Mac программно получить
нельзя — выдаются руками, см. `docs/mac-setup.md` и `README.md`.
