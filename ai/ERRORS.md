Формат: симптом → причина → как проверить/воспроизвести → решение. Команды —

## C# 5.0 без Roslyn на `csc.exe` — любой синтаксис C# 6+ падает с CS0103/CS0246

**Задачи:** 1, 16–24 (весь Windows-код).

**Симптом:** сборка через `win/build.ps1` падает пачкой ошибок вида
`CS0103: имя "Config" не существует в текущем контексте` или
`CS0246: не удается найти тип или пространство имен "IClipboardReader"` —
хотя нужный класс объявлен и лежит рядом в том же каталоге. Ошибки не про
отсутствующий тип, а про синтаксис, который компилятор не смог разобрать
чуть раньше в том же файле, из-за чего он вообще не увидел объявление.

**Причина:** сборка идёт `csc.exe` из `Framework64\v4.0.30319` (легаси-
компилятор .NET Framework, НЕ Roslyn) без NuGet и без SDK — единственный
компилятор, доступный на этой машине без установки чего-либо. Он понимает
только **C# 5.0**: запрещены интерполяция строк (`$"..."`), null-условные
операторы (`?.`, `?[`), `nameof(...)`, `out var`, `using static`,
expression-bodied члены, кортежи, pattern matching, локальные функции —
весь синтаксис C# 6 и новее. Любое такое выражение где угодно в файле
компилятор не может разобрать и в результате не видит остальные объявления
в этом же файле — отсюда обманчивые «тип не найден» вместо честной ошибки
синтаксиса.

**Как проверить:** пересобрать через реальный `csc.exe` на ПК —
`./scripts/sync-win.sh` (копирует `win/` и гоняет `win/build.ps1` по SSH).
Локальной Windows-сборки нет и быть не может — только эта.

**Отдельная, но смежная путаница: версия языка ≠ версия библиотеки.**
Ограничение C# 5.0 — это ограничение самого компилятора (запрещённый
синтаксис), а не рантайма. Целевой рантайм — .NET Framework **4.8**, и типы
`mscorlib.dll`, появившиеся в более новых версиях библиотеки (например,
`System.Runtime.ExceptionServices.ExceptionDispatchInfo`, добавленный в
.NET 4.5), доступны без дополнительных ссылок и без нового синтаксиса —
использовать их можно свободно, старым синтаксисом C# 5.0. Ошибочный вывод
«тип X недоступен, потому что требует .NET 4.5, а мы ограничены C# 5.0»
смешивает эти два независимых измерения.

**Решение:** писать только C# 5.0 (конкатенация строк вместо интерполяции,
явные `if`/null-проверки вместо `?.`, обычные методы вместо expression-
bodied) и не бояться использовать API из более новых версий `mscorlib`,
если целевой рантайм (.NET Framework 4.8) их поддерживает.

**Файлы:** весь `win/src/*.cs`, `win/tests/*.cs`, `win/build.ps1`.

## PowerShell-скрипт с кириллицей без BOM ломается при запуске через `powershell.exe` (Windows PowerShell 5.1)

**Задача:** 25 (`scripts/install-win.ps1`).

**Симптом:** первый прогон `install-win.ps1` на ПК падает с ошибками
разбора PowerShell прямо на кириллических комментариях/строках, хотя тот же
файл прекрасно читается локально и в редакторе.

**Причина:** файл был сохранён в UTF-8 **без BOM**. `powershell.exe`
(Windows PowerShell 5.1, встроенная в систему) без BOM трактует `.ps1` как
файл в системной кодовой странице, а не UTF-8 — кириллица ломает разбор
скрипта на месте. `win/build.ps1` эту проблему не ловит, потому что его
всегда запускают уже из-под открытой сессии `pwsh` (PowerShell 7) через
`& '...'` изнутри `sync-win.sh` — `pwsh` по умолчанию читает файлы без BOM
как UTF-8, `powershell.exe` — нет.

**Решение:** любой `.ps1`-файл в этом проекте с русскими комментариями или
строками, который может быть вызван напрямую через `powershell.exe`
(а не только из-под уже запущенного `pwsh`), должен сохраняться в UTF-8
**с BOM**. Так файл одинаково корректно читается и `powershell.exe`, и
`pwsh`, независимо от того, кто и как его запустит.

**Внимание, не перепутать с другим BOM:** для генерируемого `config.json`
верно ПРОТИВОПОЛОЖНОЕ правило — `[IO.File]::WriteAllText(...,
(New-Object System.Text.UTF8Encoding($false)))` пишет БЕЗ BOM намеренно,
потому что `Config.Load`/`Config.load` на обеих платформах читают файл как
обычный UTF-8 JSON и не ожидают BOM в начале. Это два независимых файла с
противоположными требованиями к BOM, оба в `install-win.ps1`.

**Файлы:** `scripts/install-win.ps1`.

## macOS: разрешения Accessibility и Local Network нельзя получить программно, и диалог может не показаться фоновому процессу

**Задачи:** 14, 15, 27 (документация).

**Симптом:** после установки и запуска LaunchAgent хоткей Ctrl+Shift+V либо
вообще не синтезирует вставку (буфер наполняется, вставки не происходит),
либо агент не видит соседа по локальной сети, при этом никакой ошибки в
логе нет и в терминале ничего не падает.

**Причина:** оба разрешения относятся к macOS TCC (Transparency, Consent
and Control) и не могут быть выданы программно ни при каких обстоятельствах
— только явным кликом пользователя в Системных настройках. Дополнительная
сложность с **Local Network**: на macOS 15+ система может вообще не
показать диалог запроса фоновому процессу, запущенному через LaunchAgent —
диалог гарантированно появляется только при первом запуске бинарника
интерактивно, из открытого Терминала.

**Решение:**
1. **Accessibility** — Системные настройки → Конфиденциальность и
   безопасность → Accessibility → «+» → выбрать точный путь
   `~/.local/bin/lanclipd` (Cmd+Shift+G в диалоге выбора файла) → включить
   тумблер. Разрешение привязано к паре (путь, подпись) бинарника — отсюда
   требование стабильного пути и ad-hoc подписи в `install-mac.sh` (см.
   `ai/FEATURES.md`): пересборка без этих двух условий сбрасывает выданное
   разрешение.
2. **Local Network** — первый запуск обязательно руками:
   ```bash
   launchctl bootout gui/$(id -u)/space.paulislava.lanclip
   ~/.local/bin/lanclipd serve --config ~/.config/lanclip/config.json
   ```
   дождаться диалога, разрешить, остановить (Ctrl+C), вернуть LaunchAgent:
   ```bash
   launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/space.paulislava.lanclip.plist
   ```
3. Если тумблер Accessibility уже включён, но не работает — выключить и
   включить заново: macOS иногда кеширует старое разрешение по старой
   подписи бинарника после пересборки.

Ни то, ни другое разрешение агентом-исполнителем задач в этом проекте не
выдавалось и не имитировалось — только человек кликает.

**Файлы:** `scripts/install-mac.sh`, `docs/mac-setup.md`,
`mac/Sources/lanclipd/MacHotkey.swift`.

## Windows: `HttpListener` на `http://+:<port>/` без urlacl падает `403 Access Denied`, а с явным хостом (тесты) — нет

**Задача:** 19, 25.

**Симптом:** `HttpListener.Start()` с префиксом `http://+:8901/` бросает
`HttpListenerException` («Access is denied») у неэлевированного процесса,
хотя тот же код с префиксом `http://127.0.0.1:8901/` работает без единой
дополнительной настройки.

**Причина:** `+` (и `*`) — это «сильный» (strong/wildcard) hostname-
префикс HTTP.sys: биндинг на него требует либо прав администратора, либо
явной резервации через `netsh http add urlacl url=http://+:<port>/
user=<домен>\<пользователь>`. Явный хост (`127.0.0.1`, конкретное имя) —
«слабый» префикс, urlacl не нужен вообще, независимо от прав процесса.
Отсюда два конструктора `HttpServer` в `win/src/HttpServer.cs`: рабочий
(`bindHost="+"` по умолчанию, нужен urlacl) и тестовый (явный `bindHost`,
используется только тестами этого файла).

**Как проверить:**
```powershell
netsh http show urlacl url=http://+:8901/
```
Пусто — резервации нет, `serve` в проде упадёт с `403`, если процесс не от
администратора.

**Решение:** `scripts/install-win.ps1` создаёт urlacl автоматически при
установке (нужны права администратора у самого скрипта); идемпотентно —
если резервация уже принадлежит текущему пользователю, пересоздаётся, если
чужая — скрипт останавливается с явной ошибкой, не трогая чужое.

**Файлы:** `win/src/HttpServer.cs`, `scripts/install-win.ps1`.

## Синтез Ctrl+V/Cmd+V поверх физически зажатых Ctrl+Shift от самого хоткея — приёмник видит лишние модификаторы

**Задачи:** 14, 24.

**Симптом на Windows (единственный класс, что удалось пронаблюдать
напрямую, и то не в чистом виде):** попытка проверить `Paste.Send()`
собственным тестовым окном (`PasteTest.exe`, не часть репозитория) не
дала вставки в это окно вовсе — окно не получило фокуса (Windows не отдаёт
фокус вновь запущенному фоновому процессу при активном пользователе,
foreground lock), и синтетические нажатия ушли в неизвестное окно на
активном рабочем столе Павла. Инцидент немедленно остановлен, процесс и
временные файлы убраны — подробности в отчёте задачи 24. Реальная
проверка вставки в постороннее окно с тех пор явно запрещена (см. README.md,
раздел про хоткей).

**Причина (по коду, не по наблюдаемому багу):** в момент срабатывания
хоткея Ctrl и Shift физически зажаты пользователем — это часть самой
комбинации Ctrl+Shift+V. Простая отправка Cmd+V/Ctrl+V поверх них выглядела
бы для приложения-приёмника как Cmd+Ctrl+Shift+V/Ctrl+Shift+V и, скорее
всего, была бы проигнорирована или воспринята иначе, чем обычная вставка —
то есть хоткей сработал бы и буфер наполнился, но пользователь увидел бы
это как «вставка не работает».

**Решение, заложенное сразу в реализацию обеих платформ** (не патч поверх
бага, а часть исходного дизайна `synthesizePaste()`/`Paste.Send()`): перед
синтезом V явно посылается `keyUp` для всех вариантов Ctrl/Shift (общий код
клавиши и оба конкретных — левый/правый, на случай если приёмник следит за
ними раздельно), даётся пауза 20 мс на обработку снятия модификаторов, и
только затем — синтетическое нажатие V с нужным модификатором. Полная
последовательность (все `keyUp`/`keyDown`) отправляется целиком даже если
часть событий уже отклонена системой — обрыв на первом отказе рисковал бы
оставить модификаторы синтетически зажатыми без парного `keyUp`.

**Смежная, отдельно найденная ошибка на Windows:** `SendInput` молча
отклонял вообще все синтетические события, потому что `Marshal.SizeOf(
typeof(INPUT))` считал размер union `MOUSEINPUT`/`KEYBDINPUT`/
`HARDWAREINPUT` по одной только `KEYBDINPUT` (24 байта) вместо истинного
размера union на x64 (32 байта → полный `INPUT` 40 байт) — `SendInput`
документированно отклоняет вызов целиком, если `cbSize` не совпадает с
реальным размером структуры. Найдено ревью задачи 24, исправлено явным
объявлением всех трёх веток union в `[StructLayout(LayoutKind.Explicit)]`.

**Проверка настоящего физического нажатия Ctrl+Shift+V остаётся на Павле**
— см. README.md, раздел «Как проверить хоткей вручную».

**Файлы:** `mac/Sources/lanclipd/MacHotkey.swift`, `win/src/Hotkey.cs`.

## Windows: SSH-сессия и интерактивный рабочий стол — разные буферы обмена

**Задача:** 22 (`win/src/WinClipboard.cs`, `win/tests/WinClipboardTests.cs`).

**Симптом:** код/тесты, обращающиеся к `System.Windows.Forms.Clipboard` через
`ssh paulislava@pc ...`, либо не видят содержимое буфера, которое реально видно
на экране ПК, либо запись в буфер из SSH-сессии никак не проявляется на
интерактивном рабочем столе.

**Причина:** OpenSSH Server на Windows работает как служба (`sshd.exe`), и
каждое SSH-соединение порождает процесс в **сессии `SessionId = 0`** —
неинтерактивной служебной сессии со своей изолированной оконной станцией
(window station) и, соответственно, своим отдельным системным буфером обмена.
Интерактивный рабочий стол пользователя (тот, что виден на экране/через RDP) —
отдельная сессия (в проверенном случае `SessionId = 1`) со своей оконной
станцией `WinSta0` и своим буфером. Буферы двух сессий не связаны и не
синхронизируются друг с другом.

**Как проверить принадлежность сессии** (команды, реально прогнанные 2026-08-18):

```powershell
# Внутри SSH-сессии (ssh paulislava@pc):
[System.Diagnostics.Process]::GetCurrentProcess().SessionId
# → 0

# Там же: какая сессия сейчас интерактивна на самой машине:
query session
# →  console       PaulIsLava             1  Активно
#    (SessionId интерактивной консоли = 1)
```

Если число из первой команды не совпадает с `SessionId` интерактивной консоли
из `query session` — сессии разные, буферы разные, результату сравнения
содержимого буфера через SSH доверять нельзя.

**Независимая проверка на живом содержимом** (не только `SessionId`, а
фактические данные — прогнано на реальной машине Павла):

```powershell
# По SSH (сессия 0):
Add-Type -AssemblyName System.Windows.Forms
[System.Windows.Forms.Clipboard]::ContainsText()   # → False (буфер сессии 0 пуст)

# Тем же кодом, но через разовую задачу планировщика в интерактивной сессии
# (см. обход ниже):
[System.Windows.Forms.Clipboard]::ContainsText()   # → True
[System.Windows.Forms.Clipboard]::GetText()        # → реальный текст с рабочего стола
```

**Обход** — разовая задача планировщика с интерактивным токеном пользователя;
создаётся и удаляется вокруг каждого прогона, ничего не остаётся на машине
после:

```powershell
Unregister-ScheduledTask -TaskName $TaskName -Confirm:$false -ErrorAction SilentlyContinue

$action    = New-ScheduledTaskAction -Execute "powershell.exe" -Argument $Command
$trigger   = New-ScheduledTaskTrigger -Once -At (Get-Date).AddSeconds(5)
$principal = New-ScheduledTaskPrincipal -UserId "PaulIsLava" -LogonType Interactive
Register-ScheduledTask -TaskName $TaskName -Action $action -Trigger $trigger `
    -Principal $principal -Force | Out-Null

Start-ScheduledTask -TaskName $TaskName
# дождаться завершения по опросу:
Get-ScheduledTaskInfo -TaskName $TaskName   # LastRunTime / LastTaskResult

Unregister-ScheduledTask -TaskName $TaskName -Confirm:$false -ErrorAction SilentlyContinue
```

`$Command` — аргументы для `powershell.exe`, обычно
`-NoProfile -ExecutionPolicy Bypass -File <путь-к-скрипту-или-exe> ...`,
перенаправляющие вывод в файл (`*> путь\output.txt`), который затем читается
обратно по SSH обычным `Get-Content`.

**Вывод:** любой код или тест, которому нужен настоящий системный буфер
интерактивного пользователя на Windows, нельзя гонять напрямую через
SSH-сессию — только через разовую `Register-ScheduledTask` с
`-LogonType Interactive` и `-UserId` этого пользователя (для резидентного
агента то же самое решено постоянной задачей с `-AtLogOn`, см.
`docs/superpowers/specs/2026-08-18-lanclip-design.md`, раздел "Известные грабли,
заложенные в дизайн" → "Сессия рабочего стола").

**Файлы:** `win/tests/WinClipboardTests.cs`, `win/src/WinClipboard.cs`.

## Диагностика с Mac уходит через корпоративный прокси и получает 503 от него, а не от соседа

**Задача:** 26 (кросс-машинная проверка).

**Симптом:** `curl http://pc:8901/health` (или любой другой запрос к соседу по
локальной сети) возвращает `503`, хотя агент на ПК жив и здоров — тот же URL,
открытый в браузере или через настроенный обход прокси, отвечает нормально.

**Причина:** в окружении Mac выставлены `HTTP_PROXY`/`http_proxy` на
корпоративный прокси, а адреса локальной подсети (`192.168.1.0/24`, mDNS-имена,
запись `pc` из `/etc/hosts`) не входят в `NO_PROXY`. `curl` и любой другой
инструмент, уважающий эти переменные, уводит запрос к соседу через прокси,
который не может до него достучаться и сам отвечает `503` — это ошибка
прокси, а не агента.

**Как проверить:**
```bash
curl -s -m 5 -o /dev/null -w "http_code=%{http_code}\n" http://pc:8901/health
# → http_code=503 (прокси)
curl -s -m 5 --noproxy '*' http://pc:8901/health
# → {"ok":false} без токена, но реальный ответ агента, а не прокси
```

**Решение:** каждый диагностический вызов к соседу с Mac обязан идти с
`curl ... --noproxy '*'`. Сами агенты (`lanclipd`/`lanclipd.exe`) не через
прокси не ходят — `NWConnection`/`HttpClient` внутри них не читают
`HTTP_PROXY` — так что сама передача буфера этой проблемой не затронута,
страдает только ручная/скриптовая диагностика с Mac-терминала.

**Файлы:** `scripts/smoke.sh`.

## PowerShell-параметры теряются при прогоне через несколько слоёв кавычек (bash → ssh → cmd.exe → powershell -File)

**Задача:** 26.

**Симптом:** `ssh paulislava@pc powershell -File runner.ps1 -ScriptPath ... -ExtraArgs "-Cmd read"` отрабатывает без ошибки (задача Task Scheduler
регистрируется и завершается с `LastTaskResult=0`), но результат выглядит так,
будто `$ExtraArgs` внутри `runner.ps1` был пустой строкой — целевой
под-скрипт получает 0 аргументов вместо ожидаемых.

**Причина:** аргументы командной строки проходят четыре независимых слоя
разбора кавычек (bash, `ssh` при склейке нескольких argv в одну командную
строку, `cmd.exe` как shell по умолчанию для команд OpenSSH на Windows,
наконец сам `powershell.exe -File`). Кавычки, которые в bash выглядят
идеально парными, на одном из промежуточных слоёв съедаются молча — без
ошибки разбора, просто с потерей значения.

**Решение:** никогда не передавать содержательные параметры через `ssh ...
-File script.ps1 -Param значение`. Вместо этого на лету генерировать
маленький вызывающий `.ps1`-файл с уже подставленными (через bash-heredoc)
путями и аргументами, заливать его на ПК через `scp` и запускать через
`ssh ... -File call.ps1` вообще без параметров командной строки — тогда
кавычки нужно свести с ума только один раз, на этапе генерации файла в
bash, а не на каждом промежуточном слое.

Похожая, но отдельная грабля: `powershell.exe -File script.ps1 *> out.txt`
не перенаправляет вывод — `*>` внутри `-Argument` для `New-ScheduledTaskAction`
передаётся как буквальный аргумент процессу, а не интерпретируется как
редирект (редиректа без шелла тут просто нет). Перенаправление должно идти
через `-Command "& 'script.ps1' *> 'out.txt'"` — там `*>` разбирает сам
PowerShell при парсинге текста команды, а не внешний шелл.

**Файлы:** тестовые хелперы задачи 26 (не в репозитории — жили в scratchpad
сессии; здесь фиксируется грабля на будущее, а не конкретный файл).

## `Get-ScheduledTaskInfo.LastTaskResult` не годится как признак завершения переиспользуемой одноразовой задачи

**Задача:** 26.

**Симптом:** обёртка вида «зарегистрировать одноразовую `ScheduledTask` →
запустить → ждать, пока `LastTaskResult` перестанет быть `267009` (task is
currently running) → прочитать файл результата» иногда возвращает результат
раньше времени — файл существует, но обрезан на первой же строке, будто
процесс ещё не успел дописать вывод.

**Причина:** при переиспользовании одного и того же `TaskName` между
прогонами `Get-ScheduledTaskInfo` в момент первой проверки (сразу после
`Register-ScheduledTask -Force` + `Start-ScheduledTask`) иногда ещё отражает
результат **предыдущего** прогона этой задачи, а не текущего — новый прогон
физически не успел стартовать, но `LastTaskResult` уже не равен `267009`
(потому что это старое, а не новое значение), и цикл ожидания выходит
немедленно.

**Решение:** не полагаться на `LastTaskResult` вовсе. Сам целевой скрипт (в
рамках той же команды, что пишет `*> out.txt`) дописывает в конец файла
результата контрольный маркер (`Add-Content out.txt '===LANCLIP_DONE==='`);
цикл ожидания опрашивает не состояние задачи, а наличие этого маркера в
файле, и только тогда считает прогон завершённым.

**Файлы:** тестовые хелперы задачи 26 (в scratchpad, не в репозитории).

## Неверный токен неотличим от «сосед выключен» в выводе `get`/`pull`

**Задача:** 26 (негативный случай из матрицы).

**Симптом:** если в конфиге вписан неверный токен (совпадающий по формату,
но не совпадающий по значению с токеном соседа), `lanclipd get`/`lanclipd.exe
get`/`pull` печатают то же самое «Сосед не найден», что и при полностью
выключенном соседе. Ни разу не появляется сообщение, упоминающее токен или
401 — то есть причину нельзя понять по одному только выводу команды.

**Причина:** `PeerResolver.resolve()` (`mac/Sources/LanClipCore/PeerResolver.swift`,
зеркало `win/src/PeerResolver.cs`) перебирает `config.peers` и считает соседа
живым только если health-проба вернула успех; `/health` на стороне сервера
сам требует совпадения токена (`HttpServer` возвращает `401` до какой-либо
бизнес-логики). Однократный CLI-вызов (`get`/`pull`) всегда начинает с
пустого кеша резолвера, поэтому неверный токен проваливает пробу для
**каждого** адреса в `peers` точно так же, как если бы там никто не слушал
порт — `resolve()` в обоих случаях возвращает `nil`, а вызывающий код видит
только этот один исход и не имеет доступа к причине (401 vs connection
refused/timeout).

**Как проверить:**
```bash
# конфиг с корректным peers, но неверным token → тот же вывод, что при
# полностью выключенном соседе:
lanclipd get --config /path/to/config-with-wrong-token.json
# → Сосед не найден
```

**Вывод:** формально требование брифа («внятное уведомление, а не тишина»)
выполнено — программа не молчит и не падает, — но сообщение вводит в
заблуждение: пользователь, ошибившийся в токене, будет чинить сеть/firewall
вместо того, чтобы перепроверить токен. Сообщено в отчёте задачи 26 как
находка для отдельного решения, без правки кода в обход ревью.

**Файлы:** `mac/Sources/LanClipCore/PeerResolver.swift`, `win/src/PeerResolver.cs`,
`mac/Sources/lanclipd/main.swift` (`runGet`/`runPull`), `win/src/Program.cs`
(`RunGet`/`RunPull`).

## Кириллица и эмодзи искажаются при печати через `Write-Output *> file` в PowerShell-консоли ПК

**Задача:** 26.

**Симптом:** диагностический PowerShell-скрипт, вызванный через одноразовую
задачу планировщика, печатает кириллический текст как мешанину символов, а
эмодзи и вовсе заменяются на `?`/`????`, хотя реальное содержимое буфера
обмена (проверено отдельно через SHA-256 и Base64 от UTF-8-байт) побайтово
корректно.

**Причина:** перенаправление `*> out.txt` кодирует вывод в кодовую страницу
консоли текущей Windows-локали (не UTF-8). Кириллица в этой кодировке хотя
бы обратимо искажается (мохибейк), но эмодзи вне её репертуара заменяются на
`?` необратимо, ещё на этапе записи в файл — это не баг lanclip, а
особенность самого способа получить диагностический вывод.

**Решение (для тестовой обвязки, не для продукта):** никогда не сравнивать
текстовое содержимое буфера, полученное через `Write-Output`, "на глаз" —
только через SHA-256 хеш и/или Base64 от `[System.Text.Encoding]::UTF8.
GetBytes($text)`, посчитанные до печати. Имена файлов такому же контролю не
подвергались отдельно (сравнивались через хеш содержимого) — искажённое имя
в логе не означает искажённого имени на диске (проверено: реальные имена с
кириллицей после `pull` совпадают побайтово).

**Файлы:** тестовые хелперы задачи 26 (в scratchpad, не в репозитории).

## `409 changedMidTransfer` воспроизводился ~20% на ПК; причина не установлена, чинится клиентским повтором, а не догадкой о причине

**Задача:** 26 (матрица содержимого, случай "имена с пробелами и
кириллицей", направление ПК → Mac).

**Симптом:** `lanclipd pull`/`lanclipd.exe pull` иногда завершается ошибкой
«Буфер соседа изменился прямо во время передачи. Попробуйте ещё раз.»
(`PullError.changedMidTransfer`/`PullException.CodeChanged`, HTTP 409 при
скачивании блоба), хотя буфер соседа между двумя запросами (манифест и
блоб) никто сознательно не трогал.

**Измеренная частота (10 повторов подряд, сценарий: 2 файла с
кириллицей/пробелами в именах, содержимое кладётся на буфер ПК через
одноразовый PowerShell-скрипт, сразу за этим — `lanclipd pull` с Mac):**
**2 из 10 (20%)** — попытки 7 и 8 из 10 упали видимой пользователю ошибкой,
остальные 8 прошли успешно.

**Первая гипотеза была ошибочной — задокументировано как урок, а не как
результат.** Первая версия этой записи утверждала, что гонка — артефакт
тестовой обвязки: якобы `Clipboard.SetDataObject(data, true)`, вызванный из
короткоживущего PowerShell-скрипта без насоса сообщений Windows, не успевает
синхронно завершить OLE-рендеринг, и добавленная после вызова `Start-Sleep`
экспериментально убирала гонку (0 из 10 с задержкой). Ревью разобрало это
рассуждение и нашло две дыры:
- **Механизм не сходится.** Флаг `copy: true` в `SetDataObject` по контракту
  WinForms заставляет `OleFlushClipboard()` выполниться СИНХРОННО, до
  возврата из вызова, — в этом и есть его смысл: данные обязаны пережить
  выход процесса-писателя. `Start-Sleep`, поставленный ПОСЛЕ этого вызова,
  физически не может повлиять на рендеринг, который уже завершился к этому
  моменту, — то есть не мог быть причиной наблюдаемого улучшения.
- **10 прогонов слишком мало.** И "2 из 10", и "0 из 10 с задержкой" —
  выборки по 10 наблюдений. Если истинная частота после изменения была,
  скажем, 10%, увидеть 0 из 10 — обычное дело, а не доказательство, что
  причина устранена.

**Проверенная и по-прежнему отклонённая гипотеза:** "журнал буфера обмена"
Windows (Win+V). Проверено через реестр интерактивной сессии Павла
(`HKCU:\Software\Microsoft\Clipboard`, значение `EnableClipboardHistory`) —
свойство не выставлено (журнал не включён явно, по умолчанию в Windows он
выключен). Также замерена сама `GetClipboardSequenceNumber()` в покое (10
замеров по 300мс) и сразу после установки содержимого — оба раза стабильна,
спонтанных изменений не поймано. Эта гипотеза отклонена, но других
проверенных гипотез не осталось.

**Итог: первопричина гонки не установлена.** Не журнал буфера обмена (сама
гипотеза отклонена измерением), но и не подтверждённая теория про насос
сообщений (рассуждение оказалось несостоятельным, а измерение — статистически
слабым). Дальнейшее расследование потребовало бы отладчика/ETW-трассировки
изменений `GetClipboardSequenceNumber()` на реальной машине — за рамками
этой задачи.

**Решение — не гадать о причине, а сделать протокол устойчивым к гонке
любой природы:** `PullClient.pull()` на обеих платформах теперь повторяет
ВЕСЬ цикл (манифест + скачивание) РОВНО ОДИН РАЗ при `changedMidTransfer` —
см. `ai/FEATURES.md`, раздел про автоповтор. После починки тот же замер (10
повторов того же сценария) дал **0 из 10 видимых пользователю отказов** —
не потому, что гонка исчезла (скорее всего, она по-прежнему происходит
где-то внутри, просто теперь прозрачно для пользователя), а потому что
клиент сам справляется с ней при первом же таком случае.

**Файлы:** `mac/Sources/LanClipCore/PullClient.swift`,
`win/src/PullClient.cs`, `win/src/Snapshot.cs`, `win/src/HttpServer.cs`.

## Диагностика картинки через `Clipboard.GetImage()` вместо реального формата "PNG" создаёт ложное впечатление потери байт

**Задача:** 26 (матрица содержимого, картинка).

**Симптом:** после `lanclipd.exe pull` картинки с Mac диагностический
скрипт, читающий буфер через `[Windows.Forms.Clipboard]::GetImage()` +
`Image.Save(..., ImageFormat.Png)`, получает PNG другого размера и с другим
SHA-256, чем исходный файл на Mac (в конкретном прогоне: 8605 байт на
входе → 3595 байт "на выходе"). Похоже на потерю данных при переносе.

**Причина: это не перенос теряет байты, а диагностика читает не тем API.**
`win/src/WinClipboard.cs:44-49,86-91,119-135,151-163` — при записи картинки
продукт кладёт исходные байты PNG на буфер под собственным соглашением о
формате `"PNG"` (`data.SetData(RawPngFormat, false, new
MemoryStream(content.Png))`) ИМЕННО ради байт-в-байт сохранности, и вторым
— `DataFormats.Bitmap` через `SetImage()` только как запасной путь для
старых/сторонних приложений, которые про формат `"PNG"` не знают (ценой
альфа-канала, задокументировано в задаче 22). При чтении (`ReadRawPng()`)
формат `"PNG"` проверяется ПЕРВЫМ и, если он есть, байты отдаются как есть,
без прогона через GDI+. К лоссовому `Clipboard.GetImage()` код обращается
только если формата `"PNG"` на буфере нет вовсе.

Диагностический скрипт читал именно этот запасной, лоссовый путь напрямую
(`GetImage()`), минуя проверку формата `"PNG"`, — то есть намеренно не тем
способом, каким читает сам продукт. Отсюда и видимая "потеря" данных: она
целиком на совести способа чтения в тесте, а не на совести переноса.

**Как проверить правильно** (зеркало `ReadRawPng()`, `win/src/
WinClipboard.cs:119-135`):
```powershell
if ([Windows.Forms.Clipboard]::ContainsData("PNG")) {
    $raw = [Windows.Forms.Clipboard]::GetData("PNG")   # MemoryStream или byte[]
    # $raw.ToArray() — те самые байты, что легли в буфер при записи, без перекодирования
}
```
После исправления оба направления (Mac→ПК и ПК→Mac одной и той же
картинки) дали идентичный SHA-256 исходному файлу — сама передача байты не
теряет. Подробности и цифры — в отчёте задачи 26.

**Файлы:** `win/src/WinClipboard.cs`.

## Волна финального ревью (2026-08-18) — грабли, которые стоит помнить

Семнадцать коммитов закрыли 14 находок финального ревью + 8 мелких пунктов
(полный разбор с тестами и файлами — `.superpowers/sdd/2026-08-18-lanclip/final-fix-report.md`).
Ниже — не пересказ диффа, а конкретные неочевидные грабли, каждая стоила
отдельного расследования.

### Сервер без дедлайна на бездействующее соединение заклинивается без единого байта токена

**Причина:** проверка токена (`X-Clip-Token`) стоит ПОСЛЕ разбора полного
HTTP-запроса — сервер должен сначала дочитать заголовки, чтобы вообще узнать,
какой токен прислали. Сосед по локальной сети (или что угодно, открывшее
TCP-соединение и замолчавшее — сканер портов, оборванный клиент, тестовый
`nc`), которое НЕ прислало токен вообще, а просто держит сокет открытым, не
даёт серверу дойти даже до этой проверки. Обработчик виснет на чтении
навсегда. Процесс при этом жив и отвечает на `ps`/`launchctl list`/Task
Scheduler — автоперезапуск (`KeepAlive`) не срабатывает, потому что перезапускать
нечего, процесс не упал.

**Решение:** дедлайн (`requestDeadline`, 8с по умолчанию) на получение ПОЛНОГО
запроса, отдельно от токена — если запрос не собран целиком за это время,
соединение обрывается независимо от содержимого.

**Файлы:** `mac/Sources/LanClipCore/HttpServer.swift`.

### Единый таймаут на всю операцию против таймаута на прогресс

**Причина:** таймаут, заведённый один раз до старта соединения и снимаемый
только после полной записи тела, превращает размер файла в скрытый параметр
надёжности — крупный блоб по Wi-Fi гарантированно упирается в фиксированный
бюджет (например, 10с), даже если данные исправно текут, просто медленно.
Различие принципиальное: таймаут ДОЛЖЕН защищать от простоя (ничего не
происходит), а не от долгой, но живой передачи.

**Решение:** развести `timeout` (время до первого байта) и `progressTimeout`
(время между чанками, сбрасывается при каждом полученном непустом чанке).

**Файлы:** `mac/Sources/LanClipCore/HttpClient.swift`, `win/src/HttpClient.cs`
(`request.ReadWriteTimeout`).

### `HttpWebRequest` по умолчанию следует редиректам и переносит кастомные заголовки на новый хост

**Причина:** .NET Framework, следуя 3xx-редиректу через `HttpWebRequest`,
по умолчанию копирует заголовки запроса (включая любые кастомные, в т.ч.
`X-Clip-Token`) на хост из `Location` — сосед на той же подсети (или MITM),
знающий сам факт существования заголовка токена, мог ответить редиректом и
получить токен на чужом хосте без необходимости его угадывать.

**Решение:** `request.AllowAutoRedirect = false`; `Perform()` доработан так,
что контракт «либо 200, либо исключение» остаётся в силе и для 3xx, которые
.NET при выключенном автоследовании возвращает без исключения по умолчанию.

**Файлы:** `win/src/HttpClient.cs`.

### `Clipboard.SetText("")` бросает `ArgumentException`

**Причина:** WinForms `Clipboard.SetText()` не принимает пустую строку —
контринтуитивно, потому что пустой текст логически валиден (например,
буфер соседа реально пуст). Раньше это ломало `pull` пустого текстового
буфера с необработанным исключением.

**Решение:** пустой/`null` текст приводит к `Clipboard.Clear()` вместо
`SetText()`.

**Файлы:** `win/src/WinClipboard.cs`.

### Отдача блоба чтением файла целиком в память сводит на нет чанкование при отправке

**Причина:** даже если сама отправка по сокету идёт чанками, если сервер
сначала грузит весь файл в `byte[]`/`Data`, пиковое потребление памяти всё
равно равно размеру файла — чанкование протокола не защищает от этого, если
чтение с диска не тоже потоковое.

**Решение:** `SnapshotStore.blob()`/`Blob()` возвращают размеченный payload
(`data` vs `file(url, size)`), файлы читаются и пишутся в сокет чанками, а
не одним `Data(contentsOf:)`/`File.ReadAllBytes`.

**Файлы:** `mac/Sources/LanClipCore/{HttpMessage,HttpServer,Snapshot}.swift`,
`win/src/{HttpServer,Snapshot}.cs`.

### `pullQueue.sync` внутри колбэка серийной очереди сервера останавливает обслуживание всех запросов

**Причина:** `HttpServer.receive()` на Mac вызывал `route()` (включая
`POST /pull`) синхронно на своей серийной `queue` — если `pull()` внутри
дополнительно синхронизировался через `pullQueue.sync` (сериализация с
хоткеем), вся серийная очередь сервера оказывалась занята на всё время
одного pull. Сосед, дёрнувший `/health` в этот момент, получает тайм-аут и
считает машину мёртвой — хотя она просто занята одним медленным запросом.

**Решение:** `POST /pull` дисптчится на `DispatchQueue.global`, ответ
отправляется обратно через `self.queue`; остальные пути (`/health`, `/clip`,
`/clip/blob`) остаются на серийной `queue` без изменений, потому что не
блокируются на сети.

**Файлы:** `mac/Sources/LanClipCore/HttpServer.swift`.

### `MaxTotal` в 400 байт не влезает в `MAX_PATH`, когда корень партии сам занимает 60+ символов

**Причина:** легаси `MAX_PATH` Windows — 260 символов. Лимит длины `rel`
в 400 байт был рассчитан без учёта абсолютного пути стейджинга, в который
этот `rel` разворачивается на приёмнике — реальный измеренный корень
стейджинга (`%LOCALAPPDATA%\lanclip\incoming\<batch>`) уже занимает порядка
66 символов, и 400 + 66 далеко превышает 260.

**Решение:** `maxTotal`/`MaxTotal` снижен с 400 до 150 — совпадает с уже
существующим `maxComponent`, а не отдельно придуманное число; 150 + запас на
корень укладываются в `MAX_PATH` с большим запасом.

**Файлы:** `mac/Sources/LanClipCore/RelPath.swift`, `win/src/RelPath.cs`.

### `NotifyIcon` завязан на поток-владелец, а на ПК это единственный канал сообщений об ошибке

**Причина:** WinForms `NotifyIcon`/трей-уведомления должны вызываться с
того же потока, что их создал (главный поток приложения, крутящий
`Application.Run()`) — вызов из постороннего потока (например, из фонового
потока, где реально выполняется `pull()`) либо тихо не показывает
уведомление, либо кидает исключение в зависимости от конкретного метода.
На ПК уведомление трея — единственный способ показать пользователю причину
отказа `pull()` без открытого терминала.

**Решение:** `TrayNotifier` держит невидимый `Control` (`marshalTarget`) с
`HWND`, созданным в конструкторе на главном потоке; `Show()` проверяет
`InvokeRequired` и маршалит через `Control.Invoke`.

**Файлы:** `win/src/Notifier.cs`.

### `split(separator: ".", maxSplits: 1)` в Swift и `IndexOf('.')` в C# по-разному считают ведущую точку

**Причина:** Swift `"...".split(separator: ".")` отбрасывает ведущую пустую
подпоследовательность — база имени `.con` (файл, начинающийся с точки)
считалась `"con"` (зарезервированное Windows-имя, требует суффикса `_`).
C# `IndexOf('.')` для той же строки находит точку на позиции 0 и считает
базу пустой строкой, имя не трогая. Один и тот же файл `.con` нормализовался
по-разному на двух платформах — `.con_` на выходе с Mac против `.con` на
выходе с Windows.

**Решение:** Mac переведён на явный индекс первой точки (то же поведение,
что и C#-реализация) вместо `split(separator:)`.

**Файлы:** `mac/Sources/LanClipCore/RelPath.swift`.

### Имя файла с «ё» приезжает на Windows разложенным (NFD), потому что macOS отдаёт имена файлов в разложенной форме

**Задача:** дефект найден живым кросс-машинным тестированием после мержа
ветки.

**Симптом:** файл `отчёт.txt`, положенный в буфер на Mac, приезжает на
Windows под именем, которое выглядит идентично, но является **другой
строкой** побайтово: вместо предсоставленной `ё` (U+0451, один кодпоинт) в
имени лежит `е` (U+0435) плюс комбинирующая диакритика (U+0308) — два
кодпоинта. Живое измерение: на Mac `отчёт.txt` — девять символов, на ПК
после копирования — десять. Программа, ищущая `отчёт.txt` в
предсоставленном виде (как его набирает человек и отдаёт любой веб-сервис),
такой файл не находит. Плюс предел длины пути в `RelPath` считается в
байтах UTF-8, а NFD весит больше байт на символ с диакритикой, чем NFC —
то есть от формы зависит ещё и то, пройдёт ли путь проверку длины.

**Причина:** файловая система macOS (HFS+/APFS) отдаёт имена файлов в
разложенной форме Unicode (NFD) через POSIX API — это давнее и стабильное
поведение самой ОС, не баг конкретного вызова. `rel` в `Snapshot`/манифесте
собирается из этих имён как есть, без нормализации, и Windows добросовестно
создаёт файл под буквально переданным именем — сам он тоже ничего не
нормализует. Автоматические тесты кросс-машинной матрицы это пропустили,
потому что сверяли хеши **содержимого** файлов, а имена либо сравнивались
визуально (разложенная и предсоставленная формы неотличимы на глаз), либо
файлы создавались и читались на одной и той же машине, где расхождения нет.

**Решение:** `RelPath.normalize`/`RelPath.Normalize` приводят `raw` к
предсоставленной форме (NFC) первым делом, до разбора на компоненты и до
подсчёта длины в байтах UTF-8 — Swift: `precomposedStringWithCanonicalMapping`;
C#: `String.Normalize(NormalizationForm.FormC)`, обёрнутый в `try/catch
(ArgumentException)` (бросает на недопустимых суррогатах) с возвратом `null`
как обычным отказом нормализации. Нормализация сделана внутри `Normalize`,
а не в вызывающем коде — это часть контракта, применяется одинаково к
производителю манифеста и к приёмнику, и предел длины считается от той же
формы, в которой путь окажется на диске. `proto/PROTOCOL.md` теперь прямо
фиксирует: `rel` передаётся в NFC, приёмник вправе на это полагаться.

**Файлы:** `mac/Sources/LanClipCore/RelPath.swift`, `win/src/RelPath.cs`,
`mac/Tests/LanClipCoreTests/RelPathTests.swift`, `win/tests/RelPathTests.cs`,
`proto/PROTOCOL.md`.

**Общие файлы волны:** полный список — в
`.superpowers/sdd/2026-08-18-lanclip/final-fix-report.md`.

## Ad-hoc подпись НЕ сохраняет разрешения TCC при пересборке

**Симптом.** После любой переустановки агента на Mac `POST /pull` начинает
отвечать `noPeer(tokenRejected: false)`, хотя `curl` к соседу из терминала
даёт `200`, токен верный, оба агента живы и слушают порт. Вставка по
Ctrl+Shift+V при этом тоже молча перестаёт работать.

**Как отличить от проблем с сетью.** Запусти тот же бинарник руками:

```
~/.local/bin/lanclipd get
```

Если из терминала работает, а из-под launchd нет — дело не в сети, не в
токене и не в коде, а в разрешениях процесса. Перезапуск при заведомо
поднятой сети (`launchctl kickstart -k`) не помогает — это отличает случай
от «агент поднялся раньше сети».

**Причина.** `install-mac.sh` подписывал бинарник ad-hoc (`codesign -s -`)
именно затем, чтобы пересборка не сбрасывала разрешения. Так не работает: у
ad-hoc подписи нет устойчивой личности, её идентификатор выводится из хеша
содержимого (`lanclipd-555549446a8d…`), поэтому каждая пересборка — новая
программа с точки зрения macOS, и выданные ей Local Network и Accessibility
к новому бинарнику не относятся.

**Решение.** Подписывать сертификатом разработчика с фиксированным
идентификатором:

```
codesign -s "Apple Development: …" -i space.paulislava.lanclip --force <бинарник>
```

Это даёт устойчивое designated requirement. Проверено эмпирически: после
пересборки `cdhash` меняется, а `pull` продолжает работать без повторной
выдачи разрешений. `install-mac.sh` теперь отказывается устанавливать
агент, если подпись оказалась ad-hoc или идентификатор не тот — молчаливое
возвращение к прежнему поведению обошлось бы слишком дорого.

## Хоткей на Windows молча перестаёт работать через несколько часов

**Симптом.** Ctrl+Shift+V на ПК не вставляет и **не даёт никакого уведомления**.
Агент при этом жив, `/health` и `POST /pull` работают, `lanclipd.exe pull`
из терминала переносит буфер нормально. Сразу после установки хоткей работает,
через несколько часов — нет.

**Ложный след.** Уведомление «Забрано с соседа» печатает обработчик эндпоинта
`POST /pull`, а не обработчик хоткея. Если кто-то (или диагностика) дёргает
`/pull`, это уведомление легко принять за отклик на нажатие. Обработчик хоткея
для текста молчит при успехе — по замыслу.

**Как отличить от прочего.** Проверь, кто владеет комбинацией, из интерактивной
сессии (в нулевой сессии по SSH `RegisterHotKey` всегда отвечает 1459,
`ERROR_REQUIRES_INTERACTIVE_WINDOWSTATION`, и проверка бессмысленна):

```powershell
Add-Type -TypeDefinition 'using System; using System.Runtime.InteropServices; public class HK { [DllImport("user32.dll", SetLastError=true)] public static extern bool RegisterHotKey(IntPtr h, int id, uint mod, uint vk); [DllImport("user32.dll")] public static extern bool UnregisterHotKey(IntPtr h, int id); }'
$ok = [HK]::RegisterHotKey([IntPtr]::Zero, 9911, 6, 0x56)   # 6 = MOD_CONTROL|MOD_SHIFT, 0x56 = V
"ok=$ok err=" + [Runtime.InteropServices.Marshal]::GetLastWin32Error()
```

`ok=False err=1409` — комбинацию держит агент, всё в порядке.
`ok=True` — **никто её не держит**, то есть регистрация агента потеряна.

**Причина.** `Hotkey` лежал в локальной переменной `Main`, после чего управление
уходило в `Application.Run()`. Сборщик мусора .NET вправе счесть локальную
переменную мёртвой сразу после последнего обращения к ней — метод при этом ещё
не вернулся, — а у `NativeWindow` есть финализатор, уничтожающий HWND. Окно
умирает, `RegisterHotKey` снимается, и хоткей перестаёт работать при живом
процессе, без единого сообщения.

Подтверждено измерением: у агента, проработавшего часы, проба показывала
`ok=True` (свободно); сразу после перезапуска — `err=1409` (занято им).

**Решение.** Держать хоткей в статическом поле `Program.hotkeyHolder`. Пока
ссылка достижима из корня, финализатор не выполнится.

**Чего стоит остерегаться.** Swift-сторона тем же не болеет: там ссылку держит
локальная константа функции, которая никогда не возвращается, и ARC её не
освобождает. Перенос этого рассуждения на .NET — ошибка: там решает
достижимость, а не область видимости. Финальное ревью проекта именно так и
ошиблось, признав жизненный цикл на Windows корректным по аналогии с Mac.
